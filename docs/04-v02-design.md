## 0. 起点：一个根本问题

> 一个人有了目标，一个人做不完。他要委托别人和 Agent 一起做，并且要求：
> **做出来的东西可信（谁做的、怎么来的）、过程可监督（进行到哪、卡在哪）、每个人都知道自己该干什么（不多想、不漏做）。**

本文的每一个设计决策，都只回答「如何满足这三条」这一个问题。不做任何「因为别人也这么做」的设计。

---

## 1. 推导：从问题到七条公理

### 推导一：协作的本质是「委托」→ 树

- 委托是二元的：「我委托你」，一次只对一个人说话。
- 二元关系串联起来，自然形成**树**：我 → 你 → 他。
- 如果允许跨级指挥，就会出现双重领导与责任不清——「谁该听谁的」无法回答。
- 因此：**节点只能与相邻节点（父与子）直接交互**。责任链上每一步都有唯一责任人。
- 一个人可以同时被多个组织委托 → **多树共存**。

**⇒ 公理 1（一切皆节点）**：系统中唯一的实体是节点。组织、团队、人、Agent、工具、技能的执行位，全部是节点。
**⇒ 公理 2（树即结构）**：节点之间的唯一关系是父子；树是唯一的结构。
**⇒ 公理 3（相邻才交易）**：任何交互（给输入、交产物、传消息）只发生在父与子之间，沿链逐跳。

### 推导二：委托 = 给输入 + 收产出 → 流即 IO

- 每次委托都有两个方向：我向下给「要什么、给什么」（**I**），你向上交「做出了什么」（**O**）。
- I 沿树自上而下分解：A → B → C → D；O 沿树自下而上汇聚：D → C → B → A。
- 一个任务拆给多个下级 = 分支；结论要完整 = **汇合点必须等全部分支回流**（全等汇合）。

**⇒ 公理 4（流即 IO）**：流只有两个方向——I 自上而下、O 自下而上；分支与汇合不改变这个不变式。

### 推导三：I 可变、O 不可变 → 守恒律

- **指令需要适配**：长链上每一级都必须把上级的话翻译成下级听得懂的话，否则信息逐级失真。所以每级向下传递的 I **可以加工改写**（每一级都是自己子树的根，拥有「根的翻译权」）。
- **成果需要可信**：如果中间人可以偷改别人的成果，「谁做的、怎么来的」就再也说不清，责任链断裂。所以 O 一旦产出，传递途中**任何人不得篡改**，各级只有「通过 / 跳过 / 打回」三种权力。
- 作者改自己的成果 = 产出**新版本 O**，旧版本留在链上不可篡改——追加式账本。

**⇒ 公理 5（守恒律）**：I 可篡改（每级有加工权），O 不可篡改（每级只有放行与退回权）。

### 推导四：事实要留痕 → 消息碎片成链

- 每次相邻交易（给输入、交产物、通过、跳过、打回）都是一件「已经发生的事实」。
- 事实 = 一条带时间戳的**消息碎片**；碎片引用上一片，串成链——可追溯、不可抵赖。
- 「时间」不必单列对象：相邻交互的碎片自带时间戳，**耗时 = 碎片的派生统计**。

**⇒ 公理 6（碎片成链）**：一切交互产生消息碎片，碎片引用成链；消息是通知的产物。

### 推导五：局部决策 + 全局感知 → 根与苍天

- 每个子树需要一个决策者；整棵树的决策者是**根**。消息上行归根，根决定如何反应。
- 但根是局部视野（皇帝也看不见天边）。需要**全局观察者**感知全树、记账、统计、示警。
- 观察者一旦可以直接干预，就破坏了「委托链」的责任结构。因此观察者**只观察、只示警、不动作**。

**⇒ 公理 7（苍天观察、皇帝决策）**：根（皇帝）是唯一决策位——可把上行消息改写为新 I 向下流转，或不作为让消息止步；上帝（苍天）是全局观察者——有眼（记账统计）、不言（不干预）、只降天象（示警反馈）。

### 推导六：能力不能有第二套对象 → 一切皆节点

- Agent、技能、CI-CD 若各有各的对象与规则，系统就分裂了。
- 统一法：**能力 = 节点的配置或组合**。Agent 是节点的智能配置；SKILL 是组合进节点的部件；CI-CD 是节点挂载的动作；上帝本身也是节点，给它建子节点 = 给它加能力。

**⇒ 公理 8（能力即节点）**：不发明第二套对象；新增任何能力，都是「新建节点 / 改节点配置 / 加扩展点实现」。

## 2. 七条公理（设计灵魂）

1. **一切皆节点** —— 唯一实体。
2. **树即结构** —— 唯一关系是父子。
3. **相邻才交易** —— 交互只发生在父子之间，逐跳传递。
4. **流即 IO** —— I 自上而下、O 自下而上，分支不改不变式。
5. **守恒律** —— I 可篡改，O 不可篡改（改 = 新版本，追加式账本）。
6. **碎片成链** —— 一切交互产生消息碎片，引用成链，可追溯。
7. **苍天观察、皇帝决策** —— 根是唯一决策位；上帝只观察、统计、示警。

> 一句话：**一切皆节点；相邻才交易；流即 IO；I 可变 O 不变；碎片成链；苍天有眼、天子执政。**

> **术语说明**：「苍天/上帝」「皇帝/天子」是推导阶段的**隐喻**，用于把「观察者与决策者分离」讲清楚。产品与实现中的正式术语为：**全局 Agent**（观察一切、记账统计、提醒示警、不干预）与**根节点**（唯一决策位，即每个账户的「自己」节点）。

## 3. 对象模型

### 3.1 三类对象

| 对象 | 定义 | 关键属性 |
| --- | --- | --- |
| **节点 Node** | 树中唯一实体，一切能力与一切身份的载体 | `id`（全局唯一、算法生成）、`parentId`、`owner`（创建者）、`visibility`（private/public）、`agent`、`skills[]`、`actions[]`、`inputContract`、`outputContract`、`status` |
| **通知 Notification** | 消息机制 | 生成规则 + 传递规则（沿树逐跳上行）+ 渠道（Web / 钉钉…）；**产物 = 消息碎片** |
| **SKILL** | Agent 能力的部件，本质是 MD 文件 | `id`、`content`（MD）；与节点是**组合关系**——组合进节点，随节点存亡，不独立流转 |

### 3.2 两类流经物（不升格为对象）

| 流经物 | 定义 | 规则 |
| --- | --- | --- |
| **I 输入** | 自上而下的委托内容 | 由消息碎片承载（每次传递 = 一条「给输入」碎片）；每级可加工改写后继续下传 |
| **O 产物** | 自下而上的成果 | **版本化 + 不可篡改**；传递途中各级只能 通过 / 跳过 / 打回；剩余未消耗的输入显式作为 O 的一部分回传 |

### 3.3 消息碎片（通知的产物）

```
Message {
  id            // 全局唯一
  prevRef       // 链上父碎片引用（成链）
  fromNodeId    // 相邻交易双方（必为父子）
  toNodeId
  kind          // 给输入 | 交产物 | 通过 | 跳过 | 打回 | 超时警示 | 新I（根的改写）…
  payload
  timestamp
}
```

- **上行**：碎片逐跳向上汇聚到根；根是全树**唯一的监听者**。
- **根的改写权**：根可基于自己的理解产生 `新I` 碎片（引用原碎片），向下流转；根不动作，消息止步。
- **上帝全见**：所有碎片对上帝可见（账本），对其余节点不可见（只见与自己相邻的交易）。

## 4. 树的规则（结构、权限、可见性）

1. **自己节点不可动**：每个账户入树即得「自己」节点，不可移动、不可删除。
2. **只能向下建**：只能在自有节点之下创建新节点；分支数量不限。→ 权限天然由树推导：你只对你的子树有写权。
3. **多树共存**：一个账户可存在于任意多棵树。
4. **可见性**：自建节点默认 `private`（自己的 Agent 场景）；可选 `public` 向全系统暴露。子节点默认继承父节点可见性，可单独覆盖。
5. **相邻交易**：写操作与消息只沿父子边发生；同树非相邻节点不可直接联系。
6. **加入**：可加入上司创建的节点（成为其子），由此并入组织树。
7. **ID**：节点 ID 全局唯一，由算法生成（生成算法为遗留决策 L1）。

---

## 5. 流的规则（IO、汇合、验收）

1. **发起**：根提出本次流的目标（「木头 → 椅子」）与验收条件，向下给出初始 I。
2. **推进**：I 逐级下传（每级可加工改写）；节点按 `inputContract` 检查输入是否满足，不满足则进入「等待」态（原因记入链）。
3. **全等汇合**：分支汇合点必须等**全部**分支回流完成才继续。
4. **产出**：节点产出 O（可含「剩余木头」等未消耗输入）；O 版本化、不可篡改。
5. **验收（自下而上逐级）**：O 沿回流路径上行，每级三选一——**通过 / 跳过（放行留痕）/ 打回（沿路退回）**。
6. **完结**：O 到达根，根按验收条件判定；不满足则根产出新 I（修订要求）向下流转，进入下一轮。
7. **守恒律**：I 可篡改（加工权在每级）、O 不可篡改（修改 = 新版本，旧版留链）。
8. **验收结论与版本绑定**：每级验收结论绑定具体 O 版本；打回 = 该版本上行终止；修订 = 新版本，从生产者重新走全程验收；旧版本结论留链、不撤销，只对新版本不生效。
9. **跨树引用**：I 可引用任何**公有节点**的 O（带版本）作为材料——这是跨树协作的唯一通道；私有节点只服务自己的子树。引用的 O 不可篡改，进入本树后成为 I 的一部分，可被各级加工（守恒律跨树成立）。
10. **人机边界**：产物默认**自动上行**（能力即节点，Agent 是节点的「手」）；每级验收是人机之间的天然关卡。两个可选配置：节点设「人工确认后才交付」；根对关键节点设「必验」（禁用跳过）。
11. **死锁出口**：全等汇合下某分支永不回流时，上帝示警后由**根（皇帝）剪枝或注入新 I**——根是全树唯一的死锁解除者。

## 6. 消息机制（碎片成链）

- 一切相邻交易都产生消息碎片；**全局单链**——所有碎片按发生顺序（时间戳 + 序列号，服务端定序）串成一条总账，`prevRef` 引用前一片；一条上行消息 = 逐跳的一串碎片。
- **账本 = 消息的存储空间**：通知机制的产物只追加地落盘于账本（不可改、不可删），存储设计见 §11.1。
- 消息**不广播**：逐跳沿树传递，非相邻节点不可直接联系。
- 上行汇聚到根；根是唯一监听者，可改写为新 I 或止步。
- 渠道触达（Web 待办 / 钉钉等）是通知机制的输出之一；**消息送达 ≠ 已处理**，待办为记录、渠道为触达。

## 7. 苍天与皇帝（上帝与根）

**根 = 皇帝（天子），上帝 = 苍天。**

| 角色 | 权力 | 边界 |
| --- | --- | --- |
| **根** | 唯一决策位：监听上行消息；主动改写为新 I 向下流转；不作为则消息止步；提出目标与验收条件 | 只管本树的决策，不替子树各节点做主（各级自己是自己子树的根） |
| **上帝** | 全局观察：所有碎片留痕于账本；统计时间（谁花了多久、卡在哪）；示警（超时、异常、进度） | 不动作、不干预树；只观察、统计、反馈 |

- **结构位置**（默认决策 F）：上帝是**根的直接父节点**——「天子」的直译；二者相邻，反馈走父子通道；一个苍天照看所有树。
- **上帝的能力 = 它的子节点**：想给上帝加「自动周报」「风险预警」，就给上帝建子节点——与「能力即节点」完全一致。
- **时间**：节点上下交互的碎片自带时间戳，上帝据此聚合出时间统计；时间是派生量，无独立机制。
- **超时处置**（默认决策 C）：上帝只示警——通知根 + 转人工；自动动作后置。

## 8. 能力体系（一切皆节点）

| 能力 | 形态 | 规则 |
| --- | --- | --- |
| **Agent** | 节点的智能配置 | 内核（模型）+ 角色提示 + 引用该节点的 I/O 契约与相邻消息 |
| **SKILL** | 组合进节点的部件（MD 文件） | 属于节点、随节点存亡；Agent 执行时按需加载 |
| **CI-CD** | 节点挂载的动作（扩展点实现） | 提交 → review → 检查 → 清理 → 打包等；保持抽象，具体外部对接后置（遗留 L3） |
| **上帝的能力** | 上帝的子节点 | 与普通节点同一套机制 |

## 9. 最小状态机（三态）

状态只回答一个问题：**「此刻这个节点在干什么？」** 因此只有三个：

| 状态 | 含义 |
| --- | --- |
| **等待** | 停着——等输入、等分支回流、等验收结果、等人工处置……**为什么等，链上最新事实说了算** |
| **运行** | 动着——输入满足，能力在运转 |
| **完成** | 本轮的 O 已通过全部验收位并到达根 |

**核心原则：原因入链，不入状态。**
「待输入 / 等待汇合 / 待验收 / 打回 / 超时 / 异常」都是**事实**，以消息碎片的形式记在链上；状态机不区分它们。想解释「为什么在等」，看链上最近一条相关碎片即可。

转移由事实驱动，只有四条：

| 转移 | 驱动事实 |
| --- | --- |
| 等待 → 运行 | 全等汇合满足（输入齐） |
| 运行 → 完成 | O 通过全部验收位 |
| 完成 → 等待 | 新的 I 到达（根发起下一轮） |
| 运行 → 等待 | 被某级打回 / 超时 / 异常（上帝已示警） |

取消 = **剪枝**：节点退出树（结构性动作），不设状态。

> 画布上三种光：等待 = 琥珀（角标注明原因，来自链上最新事实）、运行 = 青色脉冲、完成 = 绿色。

## 10. 可扩展性测试（验收本设计）

1. 新增一种能力（如「代码检查」）= 新增节点类型配置，内核零改动。
2. 换 Agent 模型 = 改节点配置的 `agent.kernel`。
3. 加入一棵新树（新组织）= 零内核改动。
4. 给上帝加能力 = 给上帝建子节点。
5. 接新通知渠道 / 新 CI-CD = 新增扩展点实现 + 配置引用。
6. 新增验收环节（如「律师审阅」）= 在回流路径上插入一个节点。

**任何一条需要改内核，就说明抽象漏了，回 §1–§2 检查。**

## 11. 实现骨架（三层）

```
第 1 层 · 内核（极简，领域无关）
  树结构与相邻校验 · 流（I 下传 / O 上行）· 碎片链与账本
  守恒律执行（O 不可篡改、版本追加）· 最小状态机 · 树快照 + 追加式账本存储（§11.1）

第 2 层 · 配置（一切能力的载体，声明式数据）
  节点定义（agent / skills / actions / inputContract / outputContract）
  可见性与权限策略 · 超时与示警策略 · 通知渠道配置 · 目标与验收条件

第 3 层 · 扩展点（外部能力，接口稳定，内核不认识实现）
  AgentKernel      —— 节点智能（模型内核）
  ActionExecutor   —— CI-CD 等动作执行
  NotifierChannel  —— 渠道触达（Web / 钉钉 / …）
```

- 内核只认识「节点、父子、I、O、碎片」，不认识「Agent、钉钉、CI-CD」。
- 一切业务形态 = 配置 + 扩展点实现，与公理 8 一致。
- 持久化：树与账本分离存储，见 §11.1。

### 11.1 持久化：两份存储（树快照 + 账本日志）

| 存储 | 性质 | 策略 |
| --- | --- | --- |
| **树快照** | 可变 | 整写整读，恢复即加载 |
| **账本日志** | 只追加、不可篡改、无限增长 | 独立追加式日志文件，与树快照分离 |

账本日志的规则：

- 每次记账 = 追加一条记录并落盘；已落盘碎片不可修改、不可删除。
- **链式哈希**：碎片携带 `prevHash`（前一片的哈希），篡改任何一片即破坏后续整链——账本自带完整性证明。
- **分段**：账本按大小/时间切分为「当前写入段 + 只读旧段」；旧段封存并附校验和。
- **恢复顺序**：重放账本验证链完整 → 加载树快照 → 链尾序列号自账本恢复。
- **归档**：旧段按保留窗口归档；归档前上帝先把时间统计聚合为摘要，避免统计失全。
- **凭证隔离**：Agent 密钥、CI-CD 令牌独立存放，不进树快照、不进账本、不进 Agent 上下文。

## 12. Web 工作台（节点房间范式）

**核心心智：每个节点都是一个「房间」，进入即身处该节点之内；打开别的节点 = 换房间。**

- **默认房间 = 「我」（自己节点）**：登录后首先身处自己的节点房间；树总览只是辅助视图。
- **房间的主展示 = 能力（actions）**：节点能做什么——Agent 内核、SKILL、CI-CD 动作等扩展能力，是房间的主体内容（一切皆节点的直接体现）。
- **房间的其余区域**：
  - 头部：节点名、根节点/普通标识、三态状态、owner、目标与验收条件；
  - 子树：下级节点卡（状态 + 待办角标），点击即进入该节点的房间；
  - 产物与验收：O 版本链、通过 / 跳过 / 打回操作；
  - 上下文：收到的 I（含上游加工痕迹）、分支回流 O、相邻消息。
- **左栏 = 树导航**：以我为根的多树列表，父子层级展开，当前房间高亮；跨树（多组织）随时切换。
- **底部 = 全局 Agent 面板**：时间统计 / 提醒 / 碎片流——只读、不干预；提醒带角标。
- **根节点房间特有**：目标与验收条件提出、上行消息监听、改写为新 I、剪枝入口。
- **全局视角 = 梧桐树**：房间之上还有一层树视角——一棵树 = 一个《源》（种子 → 树干=根节点 → 树冠=组织结构），树液=流、花苞/新叶/果实=三态、风与天光=听、年轮=账本、栖凤=公有共享。完整世界观与生成规则见 [docs/07-tree-frontend-design.md](docs/07-tree-frontend-design.md)。
- 视觉基调：深黑 · 白字 · 发丝分割线 · 等宽数字（OKX 式克制）；树为几何抽象风格。

## 14. 落地顺序（最小闭环）

1. **树内核**：节点 + 父子关系 + 多树 + 只能向下建 + 可见性继承。
2. **流**：I 下传（可改写）、O 上行（不可篡改、版本化）、全等汇合。
3. **消息**：碎片成链、上行归根、根改写为新 I。
4. **上帝**：账本、时间统计、示警。
5. **能力**：Agent 配置、SKILL 组合、CI-CD 抽象动作。
6. **验收**：逐级 通过/跳过/打回。
7. **前端**：节点房间范式（默认进入自己的房间、actions 为主展示、树导航换房间、全局 Agent 面板）。

> 每一步都以 §10 的可扩展性测试自查；通过即进入下一步。

### 14.1 最小闭环验收场景（「做完」的定义）

1. 建树、开叉分支、加入上司节点；
2. 一次流跑通：I 下行 → O 上行 → 逐级验收 → 到达根；
3. 打回迭代：新版本重新走全程，旧结论留链；
4. 超时 → 上帝示警 → 根处置（剪枝或注入新 I）；
5. 根改写消息为新 I 向下流转；
6. 跨树引用公有 O 作为输入材料。
